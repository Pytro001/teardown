Teardown app map

A snapshot of how the finished app works, made from the code at the end of the build. It can drift as the code changes.

What it is

A one page web app. You give it a photo of an object; a small Node server sends the photo to Claude Sonnet 4.5 on Amazon Bedrock, which answers in a fixed JSON shape; the page draws that answer on top of your photo: numbered callouts, a part list with cards, and a "how it is made" timeline. Five examples ship with saved answers so they load instantly.

One action, end to end

Reference route (three stops)

Not toured with the builder yet; this is the route to follow.

1. The photo comes in: web/src/components/DropZone.tsx, web/src/App.tsx (onFile)

The drop zone hands the file to onFile in App. prepareFile in web/src/lib/image.ts scales it to 1280 px and turns it into base64, and requestTeardown in web/src/lib/api.ts posts it.

2. The model answers in a fixed shape: server/bedrock.mjs (analyzeImage), server/schema.mjs (validateTeardown)

The Converse request forces the report_teardown tool, so the answer is JSON that matches teardownSchema. validateTeardown checks part counts, boxes, confidence and the process list; if it fails, the server asks once more with the errors.

3. The answer is drawn: web/src/components/Overlay.tsx (layout)

layout puts each dot at the centre of its box, picks a side for the label, spaces labels so they never overlap, and swaps slots when leader lines would cross. Timing comes from web/src/film.ts (calloutAt).

To change this, start here

  • What the model is asked: SYSTEM in server/bedrock.mjs and field descriptions in server/schema.mjs.
  • Confidence words and thresholds: web/src/lib/confidence.ts.
  • Colours and type: the :root tokens at the top of web/src/styles.css.
  • Animation speed: T in web/src/film.ts.
  • The examples: scripts/samples.mjs, then npm run samples:images and npm run samples:cache.

A practice to reuse

The spec named one uncertainty before any code: are a language model's bounding boxes good enough to put dots on? The build answered it with evidence (the five sample overlays, recorded in devpost/checklist.md under Revisions) and the product absorbed the answer as a visible feature: confidence words per part and an "approximate" note. Writing the risky assumption down first, then checking it on real outputs early, works on any project that leans on a model.

Run it again

npm install, put your Bedrock token in .env, then npm run dev and open http://localhost:5303. Tests: npm test.
